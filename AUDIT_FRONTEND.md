## # 2. Карта стейта и потоков данных

В приложении используется гибридная модель управления состоянием: глобальный Zustand-стор для разделяемых данных и синхронизации с бэкендом, и локальный React-стейт (`useState`, `useRef`) для изолированных UI-состояний.

### Распределение стейта:
- **Глобальный стор (`state/store.ts`):** 
  - Данные воркспейсов (`workspaces`, `currentId`).
  - Дерево компоновки (`layout`).
  - Список запущенных агентов (`agents`).
  - Лог и статус оркестратора (`chat`, `orchestratorStatus`, `queueItems`, `draftInput`).
  - Состояние Whisper (`voiceState`, `voiceModelDownload`).
  - Задачи активного воркспейса (`tasks`).
  - Вспомогательные флаги (`showKanban`, `newWorkspaceModalOpen`, `toasts`).
- **Стор Supervisor-модуля (`state/architect.ts`):**
  - Статус Always-On супервайзера (`enabled`), сигналы агентов (`signals`) и история авто-решений (`decisions`).
- **Локальный стейт компонентов:**
  - `AgentTile.tsx`: состояние поиска в буфере, открытые контекстные меню, парсинг CLI-блоков (`CommandBlockParser`).
  - `FilesPanel.tsx`: список открытых в редакторе вкладок (`tabs`), их загрязненность (`dirty`).

### Потоки данных и реактивность:
1. **Инициализация:** При монтировании `App.tsx` шлет IPC-запросы `restoreSession()`, `listWorkspaces()`, `getCurrentWorkspace()`, наполняя Zustand-стор начальными данными.
2. **Backend-to-Frontend (События):** Шина событий Tauri транслирует обновления с бэкенда (`agent://spawned`, `agent://exit`, `chat://message`, `workspace://layout`). Обработчики в `App.tsx` ловят их и обновляют Zustand-стор, триггеря реактивный ререндер.
3. **Frontend-to-Backend (Команды):** Пользовательские действия (ввод в консоль, перетаскивание сплиттеров, клик по кнопкам спавна) вызывают RPC-команды бэкенда через модуль [ipc.ts](file:///home/camer/pigide/frontend/src/state/ipc.ts).

## # 4. UX-наблюдения

1. **Исчезновение терминалов "на лету"**: При завершении процесса агента (например, компиляция завершилась с ошибкой), тайл мгновенно удаляется из разметки. Разработчик теряет вывод терминала и не может понять причину падения, не заглядывая во внешние логи.
2. **Модальный ад**: В приложении используются нативные блокирующие вызовы `window.prompt` (при создании закладки в браузере, переименовании воркспейса) и `window.confirm`. Они блокируют весь поток выполнения WebView, выглядят нестилизованно и ухудшают нативный Desktop-опыт.
3. **Фантомный инпут при вводе путей**: В `FolderBrowser` при клике на папку в списке, путь в верхнем поле ввода обновляется, но фокус сбрасывается или пропадает визуальная индикация выделенного элемента, что дезориентирует.
4. **Неконсистентное поведение клика по голосовой кнопке**: Быстрое нажатие на `VoiceIconButton` может запустить запись и сразу же отменить ее из-за наложений событий `onMouseDown`, `onMouseUp` и `onClick`.
5. **Отсутствие индикатора загрузки истории xterm**: При переключениях вкладок или инициализации тайла происходит асинхронное чтение 64 Кб лога. В этот момент терминал висит пустым без микро-спиннера, имитируя зависание приложения.
6. **Залипание состояния Kanban**: Состояние задач на доске Kanban сбрасывается или не синхронизируется, если перейти в другой воркспейс, так как стор очищается с помощью `clearWorkspaceState()`, но задачи нового воркспейса запрашиваются только при монтировании Kanban-компонента. Если Kanban был скрыт, а потом открыт — задачи старого воркспейса могут отображаться как stale-данные.

## # 5. Перфоманс-горячие точки

### 1. Обработка live stdout в терминалах (Event Storm)
При активном выводе (например, `cargo build` или логирование в stdout) бэкенд шлет терабайты событий `agent://stdout`. Подписчик в [AgentTile.tsx:192-202](file:///home/camer/pigide/frontend/src/components/AgentTile.tsx#L192) дергается N раз на каждый пакет:
```typescript
    onAgentStdout((e) => {
      if (e.agent_id !== agent.id) return;
      const bytes = fromB64(e.data_b64);
      const filtered = parserRef.current?.feed(bytes) ?? bytes;
      term.write(filtered);
      ...
```
Если открыто 6 терминалов, браузерный поток React тратит 83% времени CPU на обработку событий, не принадлежащих конкретному тайлу, из-за линейных CPU-сравнений строк UUID.

### 2. Рекурсивный рендер сетки Allotment при ресайзе
При малейшем перемещении границы сплиттера срабатывает `onChange` в [TilingArea.tsx:96-102](file:///home/camer/pigide/frontend/src/components/TilingArea.tsx#L96):
```typescript
        onChange={(sizes) => {
          const total = sizes[0] + sizes[1];
          if (total <= 0) return;
          const r = sizes[0] / total;
          if (Math.abs(r - node.ratio) > 0.005) setRatio(path, r);
        }}
```
Функция `setRatio` обновляет стейт дерева компоновки, запуская рекурсивный рендер `renderNode` сверху вниз. Это уничтожает и пересоздает виртуальные ноды, пересчитывая стили allotment-панелей и перерисовывая не-мемоизированные тайлы агентов.

## # 7. Рекомендованные решения по открытым вопросам

На основе согласования с координатором выработаны следующие проектные решения:

1. **Логика закрытия плиток при выходе процесса (Решено: НЕ закрывать автоматически)**
   - *Решение:* Убрать автоматический вызов `closeLeaf` при наступлении события `onAgentExit`.
   - *Как сделать лучше:* Терминал агента остается открытым в состоянии `exited` с показом оверлея завершения процесса. Разработчик может изучить логи, после чего либо нажать кнопку «Respawn» (перезапустить агент в этом же контейнере), либо кликнуть на «Remove» (или крестик `[X]` на заголовке), чтобы вручную закрыть и удалить плитку из сплит-разметки.

2. **Шорткаты в текстовых полях (Решено: НЕ блокировать навигационные горячие клавиши)**
   - *Решение:* Разрешить срабатывание глобальных шорткатов навигации (таких как `ctrl+1`..`9` для переключения воркспейсов, `ctrl+k` для открытия Kanban) даже в фокусе терминала или редакторов.
   - *Как сделать лучше:* Внести в `useHotkeys.ts` список исключений для клавиш навигации. Если нажата комбинация из этого списка, то даже при `editable === true` событие перехватывается, предотвращается его передача в терминал/редактор, и срабатывает глобальный хук.

3. **Синхронизация схем контрактов бэкенда и типов TS**
   - *Как сделать лучше:* Интегрировать в Rust-код бэкенда библиотеку `ts-rs`. Она позволяет навешивать макросы `#[derive(TS)]` на структуры данных в Rust (такие как `Workspace`, `Agent`, `Task`, `ChatMessage` и др.) и автоматически генерировать TypeScript-декларации типов `.ts` при сборке проекта (`cargo test` или `cargo build`). Это полностью исключит ручные ошибки синхронизации и сэкономит время при изменении API-контракта.
